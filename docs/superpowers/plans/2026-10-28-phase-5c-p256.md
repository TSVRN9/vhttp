## Decisions (recorded)

- **D1. The group law: RULED A by the user (2026-10-28). Phase 5d proves it; no trusted witness.**
  - **The obligation.**
    - Under the frozen spec, `scalar_mult(k, P) = point_add(P, scalar_mult(k−1, P))` (p256.rs:114–124) (preflight). Computing that literally means k additions, and k goes up to 2²⁵⁶.
    - Any double-and-add step needs **`lemma_scalar_mult_double(j, P)`**: `scalar_mult(2j, P) == point_add(scalar_mult(j, P), scalar_mult(j, P))` for an on-curve P.
    - That is a consequence of the associativity of the chord-tangent law, which is a famously hard formalization: Friedl's computer-algebra proof, the Théry/Hanrot and Bartzia–Strub Coq developments, Fiat-Crypto's `fsatz`.
    - Associativity also needs `x · finv(x) ≡ 1 (mod p)`. The spec's `finv` is `pow(x, p−2)`, not an inverse, so this is Fermat's little theorem for p, which needs a machine-checked proof that p is prime (a Pratt certificate).
    - Neither associativity nor primality is in vstd. A grep finds no prime, gcd or Fermat material.
  - **Why it can't be proved here today** (planner probes, 2026-10-28, pinned Verus):
    - `by (integer_ring)` is unavailable. The error is `Please cargo build with --features singular to use integer_ring attribute`: the released binary lacks the feature, and Singular isn't installed (dnf offers Singular 4.4.1p5).
    - Z3 `nonlinear_arith` on plain ring identities:
      - the affine-vs-Jacobian doubling identity (degree 6, 3 vars) verifies, in **9.2 s**;
      - the Jacobian-add-at-Z=1 identity (degree 6, 5 vars, checked numerically true) **fails** with `assertion failed`;
      - Lagrange's four-square identity (degree 4, 8 vars) **times out at 60 s**.
    - Associativity's generic case is a polynomial identity modulo three curve equations with thousands of terms, so Z3 is out by orders of magnitude.
  - **There is no escape hatch.** `verify.sh` rejects `external_body` on proof fns (`NOT-EXEC-FN`) and greps for `axiom`, `assume(` and `admit(`.
  - **Ruling.** The user chose **(A)**. Phase 5d is written as its own plan and merged into `main` before Task 6. Its outputs, in `crate::p256_group`, are exactly the lemmas listed under "Consumes (from 5d)" in Tasks 6 and 7:
    - `lemma_scalar_mult_double`;
    - `lemma_scalar_mult_g_nonzero`, which covers D9.

    No trusted witness, external_body or TRUSTED row is added for the group law. The options are kept below as the record of what was put to the user.
  - **Options put to the user:**

      Estimated at **more than 5a + 5b + 5c combined.**
    - **(B) Trust the one statement now; discharge it in 5d. Not chosen.**
      - Add **`crypto::p256::trusted_scalar_mult_double(Ghost(j), Ghost(pt))`**. It is a private no-op exec fn, `#[verifier::external_body]`, `requires on_curve(pt)` (or Infinity), `ensures scalar_mult(2 * j, pt) == point_add(scalar_mult(j, pt), scalar_mult(j, pt))`.

- **D2. Limbs: 4 × u64, saturated, little-endian.**
  - Value: `v4(l) = l[0] + l[1]·2⁶⁴ + l[2]·2¹²⁸ + l[3]·2¹⁹²`. Write it as a linear form with literal weights, not a recursive sum, so that Z3 treats the carry chains as linear arithmetic. `v5`/`v6` do the same for the CIOS accumulator.
  - Products `a·b_j` are passed as **atoms** into linear bookkeeping lemmas (`lemma_chain4`, `lemma_acc4`, `lemma_sub_chain`). This is the probe's key move: the same identity stated inline went to rlimit.
  - `mac(a, b, c, d) -> (lo, hi)` computes `a·b + c + d` in a `u128`, with `% 2⁶⁴` and `/ 2⁶⁴` by literal. No vstd `wrapping_mul` spec is needed.
  - **Generate the limb-weight literals by script and guard them with `lemma_weights`** (`W2 == W1·W1`, …, `W5 == W4·W1`). In the probe, a hand-typed 2²⁵⁶ was really 2²⁸⁸, and only an unrelated failure exposed it.
  - Rejected: 8 × u32 (twice the carry steps) and unsaturated 5 × 52 (adds a normalization proof and no speed that matters at D5's ceiling).
- **D3. Reduction: generic Montgomery (CIOS), not Solinas.**
  - **One proof covers both moduli:** p with `mp = 1` (p ≡ −1 mod 2⁶⁴), and n with `mp = 0xccd1c8aaee00bc4f`.
  - Solinas covers only p, needs signed-carry fixups over a (−4p, 5p) range, and would still leave n needing Montgomery or Barrett.
  - **Probe (planner, 2026-10-28).** `mont_step` (one CIOS row with exact identity `r·2⁶⁴ = t + aᵢ·B + q·M` and bound `r < 2M`) plus `mont_mul` (4 rows, then a constant-time final subtract) gave **15 verified, 0 errors, 0.84 s** total. Times: `mont_mul` 183 ms, `mont_step` 159 ms, `lemma_q_zero` 25 ms.
  - **Ensures form:** `v4(r) < v4(m)` and `(v4(r) · 2²⁵⁶) % v4(m) == (v4(a) · v4(b)) % v4(m)`, requiring only `v4(b) < v4(m)` and `(m[0]·mp + 1) % 2⁶⁴ == 0`.
  - **R⁻¹ reasoning is one lemma.**
    - The abstraction is `mdec(v, m, ri) = (v · ri) % m`.
    - `lemma_mdec_mul` gives `mdec(r) == (mdec(a) · mdec(b)) % m` from the mont_mul ensures and `(R · ri) % m == 1` (probed, 0.40 s).
    - `(R · RINV_P) % p == 1` verifies by plain Z3 on literals in 0.37 s.
  - The RINV/R² constants come from the planner's Python run:
    - `RINV_P = 0xfffffffe00000003fffffffd0000000200000001fffffffe0000000300000000`;
    - `RINV_N = 0x60d066334905c1e907f8b6041e607725badef3e243566fafce1bc8f79c197c79`;
    - `R2_P = 0x4fffffffdfffffffffffffffefffffffbffffffff0000000000000003`;
    - `R2_N = 0x66e12d94f3d956202845b2392b6bec594699799c49bd6fa683244c95be79eea2`.

    Task 1 re-derives each one with `python3 -I`.
- **D4. Inversion copies the spec's Fermat formula literally, so no FLT is needed.**
  - `finv(x) = fmod(pow(x, p−2))`, and `ecdsa_s` uses `pow(k, n−2) % n`. So `mont_pow(x, e)` (square-and-multiply over the bits of a public big-endian exponent) is proven equal to `pow(mdec(x), os2ip(e)) % m`. No inverse property is ever used.
  - The exponents are the new private consts `P256_P_MINUS_2`/`P256_N_MINUS_2: [u8; 32]`, each with a `compute_only` value lemma.
  - **The loop:** for each byte j and bit b (MSB first), `r = r²`, then `if bit { r = r·x }`. The exponent is public, so the branch is allowed. The invariant is `mdec(r) == pow(mdec(x), ev) % m`, with ghost `ev = 2·ev + bit`. It uses `lemma_pow_step` (vstd `lemma_pow_adds`/`lemma_pow_multiplies`/`lemma_pow_mod_noop`, the last taking an int base, so negative spec arguments such as `finv(x2 − x1)` are covered).
  - The cost is 256 squarings plus 128 (p) or 169 (n) multiplies, the popcounts of p−2 and n−2, since the loop starts from `one` (preflight).
  - The note on `mont_pow` is `// ponytail: plain square-and-multiply over the public exponent, 256 squarings + popcount(e) multiplies (≈<measured> µs per fe_inv, release, Task 8 p256_speed); upgrade: a fixed addition chain (~115 fewer multiplies) with one exponent-arithmetic proof per step` (preflight).
  - Rejected: a fixed addition chain. It saves about 115 multiplies but needs one exponent-arithmetic proof per chain step.
- **D5. Points: affine coordinates, computing the spec's own formulas. No Jacobian or complete formulas.**
  - Projective or RCB formulas need `x · finv(x) ≡ 1` (FLT, D1) and ring identities that Z3 fails on (D1 probes).
  - So `point_add_ct` computes exactly `point_add`'s λ, x₃, y₃, with `fe_*` ops in the spec's association order and one `fe_inv` per call. The proof is structural matching plus `fmod` congruences.
  - **Special cases are branch-free:**
    - `eqx = fe_eq(x1, x2)` and `y0 = fe_is_zero(fe_add(y1, y2))`, both 0/1 masks (preflight);
    - `num`/`den` are selected between the doubling (`3x1² − 3`, `2y1`) and chord (`y2 − y1`, `x2 − x1`) forms, so there is one inversion;
    - the result is selected among `b` (a = O), `a` (b = O), O (`eqx ∧ y0`), and (x₃, y₃).
    - `finv(0) = 0` is harmless.
  - **Representation:** `struct AffPt { x: [u64; 4], y: [u64; 4], inf: u64 }` (inf ∈ {0, 1}), Montgomery-form coordinates with `v4 < p`, viewed by `spec fn pt_view`.
    - Coordinate equality as ints is limb equality, by `lemma_mdec_inj` (canonical limbs, R invertible).
  - **Ceiling.**
    - Bench: plain-Rust replica of the probed `mont_mul`, 27.3 ns release (`-O -C target-cpu=native`), 73 ns at opt-level 0.
    - Estimate: about 10.6 µs per point op and **about 5.5 ms per scalar multiplication**, roughly 50–100× RustCrypto.
    - The note on `point_add_ct` is `// ponytail: affine, one Fermat inversion (384 Montgomery multiplies) per point op, ≈<measured> ms per scalar mult (release, Task 8 p256_speed); upgrade: Jacobian or RCB complete formulas once FLT for p and the formula identities are proven (Phase 5d)` (preflight: 384, not ~383).
- **D6. Scalar multiplication: double-and-add-always, MSB first, masked select.**
  - Over the 256 bits of the big-endian scalar, each step is `D = point_add_ct(R, R)`, `A = point_add_ct(P, D)`, `R = select(bit, A, D)`.
  - **Argument order mirrors the spec.** `scalar_mult(2e+1) = point_add(P, scalar_mult(2e))` holds by one unfold, so no commutativity is needed. Commutativity would also need FLT, because the y-coordinates agree only via `λ·(x2 − x1) ≡ y2 − y1`.
  - The invariant is `pt_view(R) == scalar_mult(ev, pt_view(P))`, with ghost `ev = os2ip(prefix)·2^b + top bits`. The doubling step calls the 5d lemma `lemma_scalar_mult_double(ev, P)` (Task 6, Consumes).
  - Rejected:
    - the Montgomery ladder, whose `R1 − R0 = P` invariant needs general additivity `(a+b)P = aP + bP`, a stronger 5d obligation than D1's;
    - fixed windows, which need the same additivity plus a masked table scan.
- **D7. Scalar arithmetic mod n and RFC 6979.**
  - **Scalar ops.** `sc_*` use the same `mont_mul` with n.
  - **Reductions.** `ecdsa_h`/`bits2octets` and `ecdsa_r`'s `x mod n` are one conditional subtraction each, because every input is below 2²⁵⁶ < 2n (n > 2²⁵⁵, and x < p < 2n).
  - **`ecdsa_s`.** Computed as `sc_mul(mont_pow(k, n−2), sc_add(h, sc_mul(r, d)))`, in the spec's order.
  - **RFC 6979 state.**
    - `rfc6979_init` is four `hmac_sha256` calls over stack buffers `V ‖ 0x00 ‖ x ‖ b` (97 bytes) and `V ‖ 0x01 ‖ x ‖ b`.
    - Each rejection runs `rfc6979_state`'s one transition: `t = HMAC_K(V)`, `K = HMAC_K(t ‖ 0x00)` (a 33-byte buffer), `V = HMAC_K(t)`.
    - The candidate is `os2ip(t)`, unreduced, compared against n.
  - **Attempt loop.**
    - It is unbounded, with ghost `i` and invariant `forall j < i: !suitable(x, h1, j)` and `(K, V) == rfc6979_state(x, h1, i)`.
    - `#[verifier::exec_allows_no_decreases_clause]` sits on `p256_ecdsa_sign`. Probed: it verifies, callers need no attribute, and the gate regex does not match it. The probe covered same-crate callers only; Task 8 Step 5 confirms the cross-crate tls caller (preflight).
    - `lemma_least_suitable_unique` makes the spec's `choose` pick the found i.
    - A bounded loop can't meet the ensures, because the spec's None (no suitable i) is undecidable.
    - The partial-correctness disclosure moves to a TRUSTED row that does **not** start with `| crypto::`, which keeps the gate's attribute/row equality.
- **D8. Peer-point validation matches `sec1_decode` exactly.**
  - The checks are: length 65; first byte 0x04; x and y each < p (non-canonical values rejected); then `fe_mul(y, y)` compared with `fe_add(fe_sub(fe_mul(fe_mul(x, x), x), 3x), B)`, which is `fmod(y·y)` vs `fmod(x·x·x − 3·x + b)` in the spec's association.
  - Peer data is public, so branches are allowed here.
  - In ECDH, `scalar_mult(d, Q) = O` returns `None` at runtime, matching the spec without proving it unreachable.
- **D9. The public key's O branch: proved unreachable by 5d (ruled with D1 = A).**
  - The spec gives `Some(seq![0x00])` for O, which no `[u8; 65]` can equal. So `p256_public_key` needs dG ≠ O for d in [1, n−1].
  - Proving dG ≠ O needs n prime (another Pratt certificate), nG = O and Bezout, all on top of D1. Under ruling A, Phase 5d supplies the fact as `crate::p256_group::lemma_scalar_mult_g_nonzero` (Task 7, "Consumes (from 5d)").
  - So `p256_public_key` is total and fully verified. It has no divergence, no `exec_allows_no_decreases_clause` and no partial-correctness row.
  - The earlier options (B + divergence, B + widened witness, C) were put to the user and not chosen.
- **D10. Constant-time style (5b D6, extended).**
  - **Secret:** d, k, every RFC 6979 K/V/T, intermediate points and field values.
  - **Public:** the peer encoding, lengths, the exponents p−2 and n−2, loop counters, and the accept/retry/None outcome.
  - No branch, loop bound or index may depend on a secret: selects are masks (`bv_sel`), and comparisons accumulate `|`/`^` with no early exit (`bv_ct_zero`).
  - **Allowed public-outcome branches:**
    - `d` out of range → None;
    - candidate k out of range, r = 0 or s = 0 → retry;
    - ECDH result O → None.

    The leaks (preflight):
    - candidate k ≥ n: probability ≈ 2⁻³², the same as RustCrypto;
    - r = 0 / s = 0: ≈ 2⁻²⁵⁶;
    - `d` out of range and ECDH O: the public result only.

    Each branch carries a `// ct:` comment saying so.
  - This is reviewed by reading, since Verus cannot check timing (design non-goal).

- **`by (compute_only)`:**
  - **Allowed only** (in this phase's files p256.rs, ecdsa.rs, mont.rs; `crate::p256_group` is Phase 5d's, verified under its own rules) in `lemma_p256_consts` (p, n, b, Gx, Gy as literals), `lemma_exp_const_p` (p256.rs: `os2ip(P256_P_MINUS_2@) == p256_p() − 2`), `lemma_exp_const_n` (ecdsa.rs: the same for n) (preflight) and `lemma_g_on_curve`, each one assert per fact. The planner probe of `p256_p()` took 0.39 s for the whole file.
  - **Never** on `pow`, `finv`, `fmod` of a product (except over literal constants in `lemma_g_on_curve`) (preflight), `point_add`, `scalar_mult`, `spec_hmac_sha256`, `spec_sha256` or anything RFC 6979. `pow(x, p−2)` recurses 2²⁵⁶ deep, and the evaluator stops at its ~3 s per-assert cap (5b D1).
  - One failing compute assert breaks every focused run in the crate, so revert negative controls at once.
- **Proof patterns that worked in 5a/5b, plus this plan's probes:**
  - **Loops** carry an invariant with **one-step unfolding** of the trusted recursive spec (`pow`, `os2ip`, `scalar_mult`, `rfc6979_state`). Never unroll 256 bits.
  - **Linear bookkeeping lemmas** take products as atoms (D2). Inline sums of products go to rlimit.
  - **`hide()`** the big spec fns a proof doesn't need. Mandatory:
    - `pow` and `finv` in every exec fn except `mont_pow` and `fe_inv`. Proof lemmas may reveal them: `lemma_finv_fmod`, `lemma_pow_step`, the bytes.rs lemmas over `pow(256, n)`, and `reduce_n`'s `pow(256, 32) == 2²⁵⁶` step (preflight);
    - `point_add` and `scalar_mult` in every byte-level fn;
    - `spec_hmac_sha256` and `spec_sha256` in the scalar code.
