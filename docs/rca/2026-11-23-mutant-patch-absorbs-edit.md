# A mutant patch regenerated from a dirty tree absorbed a source edit, and the source lost it (phase 9b3)

Status: fixed in 9b3 Task 12 fix round 2b. Caught by `scripts/mutants.sh check` (tools/mutants.py `rows`).

- **Defect**:
  - 9b3 Task 12 fix round 2 edited `cl_ok_x` in crates/h3/src/message.rs (review N1: a ghost `cq` in its exit's
    `lemma_paid` term). `scripts/quick.sh h3` verified the edit.
  - Before committing, `tools/mutants/9b3-A2.patch` (a mutation of the same file) applied with an offset, so it was
    regenerated by `git apply` on the patch, `git diff -- message.rs` into the patch, then `git checkout -- message.rs`.
  - The tree still held the uncommitted N1 edit. So `git diff` wrote N1's three changed lines into the patch as
    extra hunks, and `git checkout` reverted N1 in the source.
  - Commit 4329da8 then carried N1 inside 9b3-A2.patch and not in message.rs, though its message claimed N1. The
    controller found it with a grep for `cq`.
- **Escape**:
  - `mutants.sh check` asked only that each patch apply exactly and stay inside its row's crate. The absorbed patch
    did both.
  - `mutants.sh run 9b3-A2` killed it: N1's lines only add proof, so the mutated build still failed for the stated
    reason.
  - The source without N1 verified, because N1 tightens a check and does not change behaviour. Every gate (seeds,
    gate demos, carryovers, rfc-quantity) stayed green.
  - The regeneration was a hand procedure ("regenerate it with git diff") with no clean-tree precondition. The commit
    was made from `git add -A crates tools` without reading the staged diff.
- **Class**: C6 (mutant registry integrity), new form: a registry artifact silently carrying source edits. Close to C3:
  a claim in a commit message that no gate checks.
- **Catch** (proof is not possible here: the patches are data, not code. A script check is the next item in the
  RCA README's order, so it must fail closed):
  - Each mutant's changed lines are pinned in `tools/mutants-changes.txt`. A line `<id> <digest>` holds the sha256
    (16 hex) of the patch's file names and `+`/`-` lines, without offsets or context (`tools/mutants.py changes PATCH`).
  - `mutants.py rows`, run by `mutants.sh check` and `run`, fails when:
    - the file is missing;
    - a row has no line;
    - a patch's changed lines differ from the recorded ones. The message prints the changed lines, so the absorbed
      hunks show.
  - Regenerating a patch only because its lines moved keeps the digest, so the routine case costs nothing. A changed
    mutation needs a deliberate new line.
  - Why this and not the alternatives:
    - A per-row "patch stays inside the mutated fn" rule cannot be checked from hunk headers. Their context names
      the nearest preceding fn, not the mutated one: 9b3-A2's row names `connect_x`, but its hunk header names
      `build_headers`.
    - A changed-line count in the tsv would need a column change across every tsv reader. It would also miss an
      absorbed edit that replaces as many lines as it adds.
    - A `regen` script with a clean-tree precondition would guard the procedure but not a hand regeneration.
    - The digest is checked wherever the registry is read, so it is the cheapest check that fails closed.
- **Evidence**:
  - Gate demos (`scripts/gate-demos.sh`):
    - "mutants check: a patch regenerated from a dirty tree" reproduces the procedure on the fixture and fails.
    - "... from a clean tree after its lines moved" passes.
    - "... a row whose patch has no recorded changed lines" fails.
    - "... no tools/mutants-changes.txt" fails.
  - `mutants.py rows` on the real registry with 4329da8's 9b3-A2.patch substituted fails and prints N1's three
    absorbed lines.
  - When the digests were recorded, every patch's changed lines were compared with its copy at 8b760c5 (before 9b3
    Task 12's regenerations). All 123 matched except 9b3-A2 at 4329da8, the incident. The patch was restored to its
    one mutation hunk, and N1 went into message.rs for real.
  - Residual: the digests were recorded from the patches as they were at that point. A patch that absorbed an edit
    before 8b760c5 would have been pinned as is. Patches with more than one hunk were listed for review in the 9b3
    Task 12 report.
