# RCA: 2026-11-07 repo audit (main 14a6cf1)

## 1. verify.sh did not run the workspace tests

- **Defect**: `scripts/verify.sh` ran the proofs, duvet, the CT checks and the 9r gates, but not `cargo test --workspace` (only `ct-check.sh`'s ctmir tests). The unverified shell (`crates/server`: PEM, base64, PKCS#8, the address/PathId table, spoofed-address slots) has no proofs, so its tests were its only guard and nothing gated them.
- **Escape**: tests were run by hand per task (plan Global Constraints, "cargo test --workspace stays green"), a prose rule. verify.sh's exact final line was the green signal, and it said nothing about tests.
- **Class**: C4 GATE FAIL-OPEN (the green signal omits a check the process relies on); C18 UNVERIFIED SHELL is the code it left unguarded.
- **Catch**: verify.sh runs `cargo test --workspace --locked -q` after the gate demos and fails closed on any failure, with the final line unchanged. Fail-closed gate (preference 3): the shell's correctness is not provable until the shell itself is verified (C18's open item).
- **Evidence**: with `pem_blocks` changed to accept non-blank lines outside a block (`(None, None, None) => {}`), the gate's command fails: `loader_fails_closed --- FAILED` at `crates/server/tests/shell.rs:66`, `verify.sh: cargo test failed`, exit 1. Restored afterwards.

## 2. Two 9a bugs were live on main while their fixes sat on an unmerged branch

- **Defect**: the CRYPTO window anchored at the read offset (RFC 9000 §7.5 floor, fixed by fcf9ff0, 3b23dbf) and the empty STREAM frame extending the receive buffer (fixed by 8f6b48e) were fixed and reviewed on phase-9a but still on main.
- **Escape**: the phase workflow merges once per phase, so a reviewed bug fix waits for the phase's last task; 9a's last tasks (3b, 5, 3c') are multi-session.
- **Class**: C3 CARRYOVER IN PROSE (the fix's location was tracked only in the ledger).
- **Catch**: process ruling (ledger, 2026-11-07): a task that fixes a bug present on main triggers a merge of the branch once its review passes, not at phase end. Not mechanical yet; 9r2's carryovers gate owns the mechanical form (a ledger line naming a main bug fix with no merge commit containing it fails).
- **Evidence**: this audit found both on main 14a6cf1. The merge commit that lands them is named in the 9a ledger and in `git log --merges main`.
- **Trade recorded at merge (9a final review I2):** T3's re-anchoring replaced the proved `buf_len <= 16384` with `<= unread + 16384`; the unread in-order part is bounded at runtime by quictls's drain, proved by Task 3b. TRUSTED.md carried a row for it from 981d613; 9a Task 3b proved the drain at the QuicServer boundary and drops unread bytes on close (c5634d2), restoring `buf_len <= 16384` at every pub exit, and deleted the row.

## 3. Four getrandom calls per `Rand`

- **Defect**: `crates/server/src/lib.rs`'s `rand` filled each of `Rand`'s four arrays with its own `rng` call, so every routed datagram made four `getrandom` syscalls. Fixed in f273352 (one call, split).
- **Escape**: the shell has no cost model (ct-check's cost bounds cover crates/crypto only) and no test counted calls; review read the code for correctness, not syscall count.
- **Class**: C15 ALGORITHMIC COST (cost not pinned), in C18 UNVERIFIED SHELL.
- **Catch**: the test `one_rng_call_per_datagram` (`crates/server/tests/shell.rs`) counts `rng` calls through a counting `Rng` and pins one per datagram; verify.sh now runs it (§1). A test (preference 4): the shell is unverified, so no proof obligation can state it yet.
- **Evidence**: with f273352^'s `lib.rs`, the test fails `left: 8, right: 2`.

## 4. Refed 1-RTT CRYPTO left unread: a required TLS close delayed (9a T3b review I1)

- **Defect**: `QuicServer::receive` ran `tls_step` and then `refeed_one_rtt`, which re-processes 1-RTT packets held until the keys were ready. Nothing fed OneRtt CRYPTO to TLS after the refeed, so a 1-RTT CRYPTO frame in a refed packet stayed unread until the peer's next datagram. TLS answers any client OneRtt CRYPTO byte (for example a TLS KeyUpdate, which RFC 9001 §6 forbids in QUIC: "MUST treat the receipt of a TLS KeyUpdate message as a connection error of type 0x010a") with unexpected_message, and RFC 8446 §6.2 says that on a fatal alert "both parties MUST immediately close the connection"; so that close waited for the next datagram, or never came. Introduced in 15b98bb (2026-11-05, 4c); fixed in a68b45b (phase-9a2).
- **Escape**: the drain was a property of the private step (`tls_step`), not of the pub entry the shell calls; no ensures on `receive` said "every byte accepted in this call is fed to TLS". The one coalesced test (`finished_coalesced_with_one_rtt`) carried only a PING in its 1-RTT packet, so no test put CRYPTO in a refed packet.
- **Class**: C9 COMPOSITION GAP (a per-step property that does not survive the composition the shell actually runs).
- **Catch**: proof obligation: `receive` and `accept` ensure `crypto_all_drained`, and every other pub `QuicServer` `&mut self` entry ensures `drained_kept` (a68b45b). Class-wide: 9c's quictls lift states each step's obligations at the pub API, and a lint, owner 9c (with that lift; catalog C9): every `spec fn` that a private quictls step ensures and that the design calls "between datagrams" must appear in a pub entry's ensures.
- **Evidence**: `finished_coalesced_with_one_rtt_crypto_0x10a` (quictls tests) stays Open on 14b07e9 and ends Closing with 0x10a on a68b45b; mutation F1 (delete the post-refeed feed) fails `receive`'s drain ensures.

## 5. ALPN failure before the peer's parameters closed with a generic code (9a T5)

- **Defect**: `Connection::on_handshake_complete` checked "peer transport parameters absent" (INTERNAL_ERROR) before the ALPN check, so a non-h3 ALPN with no parameters yet closed with 0x01 instead of 0x0178 (CRYPTO_ERROR + no_application_protocol, RFC 9001 §8.1). Since c4e54a9 (2026-11-02); fixed in 9a T5 (84e8377), test `alpn_mismatch_without_params`. Not reachable through the real stack (tls refuses a non-h3 ALPN itself with 0x178, emits PeerParams before Complete, and quictls always passes `H3_ALPN`), and RFC 9000 §11 allows a generic code, so it was a contract gap at the `Connection` API, not a wire bug.
- **Escape**: the fn had no close-code ensures (at c4e54a9 its only ensures were `wf` and `out_log`); none for §8.1 existed until T5, and the one non-h3 test (`alpn_mismatch`) called `on_peer_params` first, so the doubly faulty state was never exercised.
- **Class**: C7 REQUIRED CLOSE MISSING (MUST-close without its converse).
- **Catch**: proof obligation: `on_handshake_complete` ensures the §8.1 converse (`old Open && !old.live(OneRtt)` and a non-h3 ALPN ==> Closing with 0x0178), and mutation D5 deletes that close and fails it. Class-wide: rule 1b, plus two 9r2 gates (on branch phase-9r2, not yet on main when this was written): the citations gate requires a `//=` citation on every close-code fn, and the mutant registry (C6's catch) requires each close-code fn to be named by a registered mutant row.
- **Evidence**: `alpn_mismatch_without_params` reads 0x01 on 9f2aedd and 0x0178 on 84e8377; D5 fails the converse ensures.

## 6. An out-of-order duplicate CRYPTO frame cost a full fragment copy (9a T7 review I1)

- **Defect**: Task 7's `Frags::insert` (35aa074, 60982ec) did O(fragment) work for a frame whose bytes were all held already: `locate` scanned the fragment list linearly (three times per frame: `on_ooo`'s `after_insert`, `insert`'s `after_insert`, then `insert`'s own `locate`), `merged` copied every byte of the touched fragment into a new `Vec`, and `splice_in` split and re-appended the list. Measured in release on edeca5c: 7.8 µs per 1-byte duplicate inside a held 16 KiB fragment, against 4 ns on the dense store at 046da08, about 2000x the base. CRYPTO has no flow control and duplicates never reach TLS, so a peer could send them without limit: about 1.8 ms of CPU per 1200-byte datagram, unbounded per connection. Fixed in 05853c3. `locate` is now a binary search, and `insert` returns after it when one fragment holds the whole frame. That return is proved a no-op: `insert` ensures `*final == *old` when every position of the frame is held. A duplicate now costs 10 ns (4096 fragments: 27 ns).
- **Escape**: cost is in no contract. Task 7 had no cost test on the CRYPTO path; its timing test (`crypto_tail_then_in_order`) covers only in-order frames. The report stated the per-call cost but not that duplicates are unlimited. The reviewer's benchmark found it.
- **Class**: C15 ALGORITHMIC COST.
- **Catch**:
  - Proof: `Frags::insert`'s no-new-position ensures. The path is a binary search plus one comparison by construction; there is no proof of time.
  - Mechanical: `tests/crypto_alloc.rs` (`duplicate_ooo_frames_allocate_nothing`, a counting allocator). 10,000 one-byte duplicates inside a 16 KiB fragment, and over 4096 one-byte fragments, must allocate 0 bytes.
  - What remains is a frame with new positions: about 10-12 µs each, measured, bounded per level by its new positions. Per connection that is about 0.2 s at 1-RTT, 1 s at Handshake (a Finished body of up to 65536 bytes) and 1.8 s at Initial (two ClientHellos with a HelloRetryRequest), and Initial's needs no address validation or authentication.
  - Measured (9b1 Task 1, release, bd2708a): `CryptoStream::on_crypto`, a counting allocator; laptop, other load present.

    | pattern | frames | time | live bytes (requested) |
    |---|---|---|---|
    | 4096 one-byte runs, ascending | 4096 | 0.7 ms | 135168 |
    | 4096 one-byte runs, descending (slot shifting) | 4096 | 6.2 ms | 135168 |
    | one fragment grown downward a byte at a time to 16383 (byte copying) | 16383 | 108 ms | 16511 |
    | the same, each frame re-sending everything above it | 16383 | 96 ms | 16511 |
    | 4096 runs, then each gap filled | 8191 | 23.6 ms | 139263 |

    Byte copying dominates: about 6.6 µs per frame at 16 KiB held, the same order as the 10-12 µs above. `crypto_ooo_cost_linear` (`tests/crypto_cost.rs`) failed at bd2708a (passes since 9b1 Task 7, which removed its `#[ignore]`) on bounds relative to the input (w = frames + input bytes; bytes per unit of w may grow at most 1.5x per doubling): grow-down allocates 8386688 -> 33550464 -> 134209664 bytes at n = 1024/2048/4096 (w 8190 -> 16382 -> 32766), time 6.1 ms -> 94 ms; runs-then-fill 1115007 -> 4327295 -> 17043327 bytes (w 4094 -> 8190 -> 16382), 2.0 ms -> 38 ms. descending and grow-down-full pass (their cost is linear in w; the full-resend pattern's input is itself quadratic).
  - Corrected in fix round 2 (re-review n1); the first statement said 7.2 µs and 0.12/0.59 s.
  - The follow-up is Phase 9b Task 1, a Frags index (C15).
  - Fix round 2 adds a time bound to the test. 10,000 duplicates over 4096 fragments must take under 50 ms (2-6 ms in the debug test build); a linear-scan `locate` takes about 165 ms and fails it (measured at 574d0f6 against a linear `locate`).
- **Evidence**: `duplicate_ooo_frames_allocate_nothing` allocates 327600000 bytes on edeca5c's `insert` and 0 on 05853c3 (run against both commits; the logs went with the evidence directories, F19). Benchmark: the reviewer's release benchmark on edeca5c and 05853c3.
